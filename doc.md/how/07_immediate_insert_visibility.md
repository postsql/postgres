# How: User Guide for Immediate Insert Visibility

## 1. Configuring Immediate Insert Visibility

Immediate insert visibility is controlled via two GUC parameters:

| GUC Parameter | Type | Default | Description |
| :--- | :--- | :--- | :--- |
| `immediate_insert_visibility` | `boolean` | `off` | When `on`, newly inserted tuples are immediately visible to all concurrent transactions without waiting for commit. |
| `immediate_insert_wal_flush` | `boolean` | `off` | When `on`, forces a synchronous flush of WAL records generated by the insert statement before returning. |

### Server Configuration (`postgresql.conf`)
```ini
# Enable immediate visibility for the cluster
immediate_insert_visibility = on

# Control whether inserts flush WAL synchronously to disk
immediate_insert_wal_flush = off
```

### Session Configuration (SQL)
You can enable immediate visibility only in dedicated ingestion sessions or micro-batches:

```sql
-- Enable in current ingestion session
SET immediate_insert_visibility = on;
SET immediate_insert_wal_flush = off;
```

## 2. Producer-Consumer Queue Example

### Table Setup
```sql
CREATE TABLE task_queue (
    task_id BIGSERIAL PRIMARY KEY,
    payload JSONB,
    status TEXT DEFAULT 'pending',
    created_at TIMESTAMPTZ DEFAULT clock_timestamp()
);
```

### Producer Session (Writer)
A worker batches work inside a long-running transaction:
```sql
BEGIN;
SET LOCAL immediate_insert_visibility = on;

-- Insert jobs into queue
INSERT INTO task_queue (payload) VALUES ('{"action": "process_image", "id": 1}');
INSERT INTO task_queue (payload) VALUES ('{"action": "send_email", "id": 2}');

-- Producer can pause, do more work, or batch 10,000 items here...
-- The rows above are ALREADY VISIBLE to other sessions right now!
```

### Consumer Session (Concurrent Reader)
In another database connection, while the producer's transaction is still open:
```sql
-- Returns the pending tasks immediately (0 ms lag!)
SELECT * FROM task_queue WHERE status = 'pending';
```

## 3. High-Throughput IoT / Telemetry Streaming

For real-time dashboard analytics on streaming sensors:
```sql
CREATE TABLE sensor_telemetry (
    device_id INT,
    temperature DOUBLE PRECISION,
    reading_time TIMESTAMPTZ DEFAULT clock_timestamp()
);

-- Ingestion stream
SET immediate_insert_visibility = on;
SET immediate_insert_wal_flush = off;

-- High-throughput continuous insert loop
INSERT INTO sensor_telemetry (device_id, temperature)
VALUES (101, 23.4), (102, 24.1), (103, 21.9);
```
Dashboards running `SELECT avg(temperature) FROM sensor_telemetry WHERE reading_time > now() - interval '5 seconds'` observe updates instantaneously without commit overhead.

## 4. Operational Best Practices and Caveats

1. **Intended for Append-Only Rows**:
   Immediate insert visibility is specifically designed for `INSERT`. Avoid issuing `ROLLBACK` on transactions that have inserted rows under `immediate_insert_visibility = on` if concurrent readers are sensitive to seeing rolled-back tuples, as rows are stamped as committed immediately.
2. **Durability Planning**:
   If hardware or server crashes must guarantee zero data loss for individual inserts, set `immediate_insert_wal_flush = on`. If maximum throughput is preferred and OS/disk caching is acceptable, keep `immediate_insert_wal_flush = off`.
